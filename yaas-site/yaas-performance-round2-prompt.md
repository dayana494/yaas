# Задача: доработать перформанс после первого раунда

Контекст: первый раунд (коммит "Cut mobile Lighthouse TBT from 1070ms to 265ms, desktop LCP to 0.7s") дал заметный выигрыш на замерах через `vite preview` + локальный Lighthouse (mobile 73→92, desktop 91→100), но реальный прогон на https://pagespeed.web.dev дал mobile 75→69, desktop 65→69. Причина расхождения: локальный Chrome рендерит WebGL на настоящей видеокарте, а PageSpeed — программно (нет GPU), поэтому кадры влёта банок там стоят в разы дороже и почти всё выигранное TBT съедается заново. Это не баг прошлой работы — цифры по картинкам и весу страницы (2,7 МБ → ~1,3 МБ) подтвердились и на PageSpeed. В этом раунде: только пункты ниже, без повторной атаки на WebGL/TBT — она отдельная большая задача (OffscreenCanvas), тут не трогаем.

## Как теперь измерять (важно, иначе снова разойдётся с реальностью)
Локальный Lighthouse должен эмулировать отсутствие GPU, как у PageSpeed:
```
chrome --use-angle=swiftshader --enable-unsafe-swiftshader
```
(или флаги `--gpu-blocklist-test-group=2` / `chrome.flags: ['--use-gl=swiftshader']` в конфиге lighthouse, в зависимости от того, что уже используется в проекте). Проверь, что с этим флагом локальный TBT на мобильном профиле близок по порядку величины к текущему PageSpeed-замеру (mobile TBT ~1150 мс) — если совпадает с точностью до одного порядка, значит методика верна. Если под рукой уже есть npm-скрипт замера из прошлого раунда — допиши в него программный рендеринг, не создавай новый с нуля.
Итоговую проверку всё равно делай и через реальный https://pagespeed.web.dev (мобильный и десктоп), не только локально.

## Пункт 1 — мобильный LCP 2,6 с: заголовок прелоадера ждёт шрифт

В `index.html` заголовок «loading energy» использует `@font-face 'Soledago PL'` с `font-display: block`. Это специально: без него заголовок сначала рисуется в fallback-шрифте и после подгрузки Soledago сдвигается (layout shift). Но `font-display: block` означает, что на медленном 4G браузер держит текст невидимым до ~3 c или до загрузки шрифта — LCP-разбивка показывает delay 2,36 с именно на этом.

Решение: не грузить весь `Soledago.woff2` (28,8 КБ) для одного заголовка — вшить в `index.html` **сабсет** шрифта только с нужными глифами (`loading energy 0123456789%` + буквы для остального текста прелоадера, если есть) как `data:` URI прямо в инлайновом `<style>`. Инструмент — `fonttools`/`pyftsubset` (или что уже есть в devDependencies/системе; если ничего нет — спроси перед установкой). Цель: сабсет ≤ 3–5 КБ, встроен как base64 — не отдельный сетевой запрос, значит доступен в первом же кадре, независимо от скорости соединения.
Полный `Soledago.woff2` для остального сайта (логотип, заголовки блоков) не трогать — preload и `font-display: swap` там остаются как есть.

**Проверка:** на throttled Slow 4G в DevTools заголовок прелоадера виден с первого кадра (не пустой экран 2+ секунды). LCP на PageSpeed mobile ощутимо ниже 2,6 с. Визуально текст идентичен (тот же шрифт, тот же кегль).

## Пункт 2 — FCP: основной CSS блокирует отрисовку

`dist/index.html` после сборки содержит `<link rel="stylesheet" href="/assets/index-*.css">` — это Vite-инжект, блокирует рендер на 150–300 мс (render-blocking-insight в отчёте). Поскольку весь экран в это время всё равно закрыт инлайновым прелоадером (у него свой `<style>` в `<head>`, не зависящий от основного CSS), можно сделать основной CSS неблокирующим без визуального риска:

Через плагин к Vite-сборке (или через `vite-plugin-html`/ручную трансформацию в `vite.config.js` на этапе `transformIndexHtml`) превратить инжектированный `<link rel="stylesheet">` в паттерн:
```html
<link rel="preload" as="style" href="...css" onload="this.onload=null;this.rel='stylesheet'">
<noscript><link rel="stylesheet" href="...css"></noscript>
```
Не делай это руками в `index.html` — исходный файл шаблон, а не финальный; правка должна жить в сборке (Vite-плагин или post-build скрипт, который трогает `dist/index.html` после `vite build`, и такой шаг тогда добавляется в `package.json` → `build`). Посмотри, есть ли в проекте уже похожий post-build шаг для чего-то другого (например, для генерации `-1280.webp`/`-sm.webp` из прошлого раунда) — если да, пристройся к нему, а не создавай отдельный.

**Проверка:** страница визуально не мигает нестилизованным контентом (просто не должна — прелоадер всё закрывает первые 2 секунды). FCP на PageSpeed не хуже текущего, ожидаемо немного лучше.

## Пункт 5 — по мелочи, десктоп и общее

- **Forced reflow 98 мс, `index-*.js:27:1872`.** Найди источник (скорее всего resize/measure хук в общем чанке — `useHeroScale.js`, `onRealResize.js` или что-то в `main.jsx`/`App.jsx`, минифицированную строку сматчи через sourcemap или `npm run build -- --sourcemap` временно). Если это чтение `getBoundingClientRect`/`offsetWidth` сразу после записи стиля — развести на "сначала все чтения, потом все записи", как уже сделано в риск-драйверах прошлого раунда (`riseTransition.js`). Не трогай, если источник — сторонняя библиотека (three/gsap), туда лезть не надо.
- **`can.glb` в конце цепочки запросов.** Сеть-дерево показывает: `index.js → HomePage.js → Scene.js → useCanMaterials.js → can.glb`, задержка до начала загрузки модели ~1–2,5 с. Добавь `<link rel="preload" as="fetch" crossorigin>` на URL `can.glb` в `index.html` (используй ту же `%BASE_URL%` подстановку, что у шрифтов), чтобы браузер начал качать файл параллельно с JS-цепочкой, а не после неё. Проверь, что `useGLTF.preload(MODEL_URL)` (`useCanGeometry.js`) продолжает работать корректно (не задвоится сеть-запрос — should be same URL, browser dedupes).
- **Картинки about-brand (`about-brand-1.jpg`, `about-brand-2.jpg`, 137+134 КБ) с `loading="lazy"` всё равно попадают в cache-insight/сетевой лист первой загрузки на десктопе.** Проверь `BrandTeaserScreen.jsx:416` — если секция реально далеко от первого экрана, `loading="lazy"` должно быть достаточно; если браузер всё равно тянет их рано, добавь `fetchpriority="low"` рядом с `loading="lazy"` (лишним не будет) и убедись, что родительский контейнер не имеет `display: none`/нулевую высоту при маунте (из-за чего браузер может считать картинку "видимой" и грузить сразу).
