# Правка: автоскейл блоков по всему сайту

Задача по сайту YAAS (`yaas-site`): на сайте есть блоки, у которых нет автоскейла — их нужно найти и добавить автоскейл, не изменив визуал ни на одном разрешении.

## Суть задачи

Автоскейл должен быть у **всех** блоков сайта — то есть размеры/отступы/позиционирование должны меняться непрерывно и пропорционально вместе с шириной/высотой вьюпорта (как это уже сделано через `--hero-scale` в хиро-стейдже и через `clamp()`/`vw`/`svh` в резиновой раскладке остальных блоков), а не оставаться одним и тем же числом в пикселях сразу для целого диапазона ширин (например "одно и то же значение что для 769px, что для 1023px, что для 1920px").

Это не визуальный редизайн: на тех ширинах/устройствах, где сейчас всё выглядит правильно, после правки не должно быть ни одного визуального отличия — ни на пиксель, и уж тем более контент не должен увеличиться.

Два существующих механизма адаптивности на сайте, для справки:

- **Фиксированный стейдж + `scale()`** (`hooks/useHeroScale.js`, `--hero-scale`) — используется только в `HeroScreen.jsx` (хиро на главной) и в первом экране `FlavorStorySection.jsx` (шапка страницы вкуса). Единственное место, где контент вписывается в вьюпорт масштабированием целой панели (1200×650), а не резиновой версткой.
- **Резиновая типографика/отступы через `clamp()`/`vw`/`svh`** — всё остальное: `Screen2`/`ScenarioArcGallery`/`ScenarioCardsIsometric`, `AdvantagesScreen`, `BrandTeaserScreen`, `FaqScreen`, `ContactSection`, `Footer`, `FlavorGallery` ("Try the Other Flavors"), общая шкала `--block-heading`/`--block-gap`/`--content-gutter` в `styles/index.css`.

## Что считать "нет автоскейла"

Критерий отбора кандидатов: свойство влияет на видимый размер/положение блока (`width`, `height`, `min-width`, `min-height`, `padding`, `margin`, `gap`/`row-gap`/`column-gap`, `top`/`left`/`right`/`bottom`, `font-size`) и задано голым числом в `px`, без `clamp()`, без `vw`/`vh`/`svh`/`svw`/`dvh` и без `calc(var(--hero-scale) * …)` — то есть число, которое физически не может измениться при изменении вьюпорта, кроме как скачком на следующей `@media`-границе.

Не считать кандидатом (заведомо намеренно фиксированные вещи — трогать не надо, это регрессия, а не фикс):

- `max-width` как потолок уже резинового контента (например `max-width: 640px` на тексте, который и так сужается через `clamp()`/`%` ниже этого потолка, `content-max: 1340px`) — обычный паттерн.
- декоративный `border-radius` (скругление карточек, "таблеток" — `20px`, `100px` и т.п.) — почти всегда можно оставить фиксированным.
- волосяные обводки (`border: 1px solid …`).
- минимальные тач-таргеты (`min-height: 44px` у `.hero-pill`/`.hero-cta`) — стандарт доступности, должен оставаться физическим размером пальца, а не резиновым.
- `letter-spacing` (микроправки типографики).
- уже задокументированная в коде осознанная **ступенчатая** (не непрерывная) система: сайтовый базовый текст "16px десктоп / 14px мобильный" (см. комментарии "Site-wide text scale"/"Site-wide body-copy size" в `hero.css`/`layout.css`/`advantages.css`) — это два фиксированных значения по всему сайту специально, а не пропущенная резиновая шкала; не превращай в `clamp()`, если отдельно не попросят.

## Отправная точка — уже нашёл кандидатов (черновой список, не финальное ТЗ)

Прогнал по всем файлам `src/styles/*.css` фильтр "px-значение без `clamp()`" (команда — ниже). Стоит проверить в первую очередь — то есть точно не покрыто автоскейлом сейчас, но неизвестно, ломает ли это что-то визуально:

- `styles/flavor-detail.css`, `@media (min-width: 1024px)`, блок абсолютного позиционирования мокапа галереи (`top: 114px`; `left: 196px/444px/809px`; `width: 809px/312px/391px/1024px`; `--caption-top: 625px`) — всё голыми px, привязано к десктопному макету; на промежуточных десктопных ширинах (1280–1366) и на ultrawide (2560px+) эти абсолютные px не масштабируются вместе с остальным резиновым контентом секции.
- `styles/screen2.css`, блок карточки со ссылкой снизу (`left/right: 30px` → мобильный `20px`; `bottom: 20px`/`16px`) — фиксировано отдельно внутри каждого брейкпоинта, ступенчато, без перехода между ними.
- `styles/layout.css` — три независимых фиксированных набора размеров иконки/превью на три брейкпоинта (`83px/109px`, `56px/56px`, `48px/64px`) с резким скачком между ними вместо перехода.
- `styles/contact.css` — `min-height: 420px` и `min-width: 280px` на панели контактов: не резиновые, могут стать непропорционально маленькими/большими на нетипичной ширине контейнера.
- `styles/advantages.css`, `@media (min-width: 769px) and (max-width: 1023px) and (orientation: landscape)` — `height: 520px` у карточки: фиксированная высота именно в планшетном диапазоне, не привязана ни к `vh`, ни к `aspect-ratio`.
- `styles/faq.css` — иконка плюс/минус аккордеона (`width/height: 40px`, полоски `14px`/`2px`) — вероятно, можно оставить как декоративную мелочь, но включи в проверку на 320px.

Это не техзадание "поправь ровно эти строки", а отправная точка. Пройдись этим же способом по всем 11 файлам `styles/*.css` и по инлайн-`px` в `.jsx`/данных, которые управляют версткой DOM-блоков (`data/layout.js`, `data/contactLayout.js` и т.п. — не Three.js-сцены, там свои единицы), и по каждой находке реши: реальный кандидат или намеренно фиксированное значение (см. критерии выше).

Команда для поиска:

```bash
grep -nE ':\s*-?[0-9]+(\.[0-9]+)?px' src/styles/*.css | grep -v 'clamp('
```

(дальше глазами отфильтровать `border`, `letter-spacing`, `min-height: 44px`, декоративный `border-radius`, ступенчатый sitewide body-текст — как описано выше).

## Как чинить, не меняя визуал

Для каждого подтверждённого кандидата: не переписывай число на "чистый" `vw` — это точно изменит вид на текущих ширинах. Вместо этого — оборачивай в `clamp()`, где сегодняшнее фиксированное значение становится полом/потолком, а между уже протестированными опорными ширинами (границы существующих `@media`, плюс обычные "паспортные" ширины: 375, 768/769, 1023/1024, 1440, 1920) значение плавно интерполируется, но нигде не превышает и не занижает то, что есть сегодня на этих опорных ширинах. Делай по образцу уже существующих переменных в `styles/index.css` (`--block-heading`, `--advantages-inset` и т.п.) и по образцу мест в `flavor-detail.css`/`hero.css`, где такой пересчёт из фиксированных px в `vw`/`svh` уже делался с пояснением "откуда взялось число" в комментарии — делай так же: пиши в комментарии, из какого px и на какой опорной ширине выведена формула.

## Ограничения

- Только эта задача. Не трогай перформанс/WebGL/scroll-timing логику и не относящуюся к автоскейлу верстку (см. `yaas-performance-round2-prompt.md` — там уже есть отдельно защищённые от правок куски).
- Это ревизия на предмет пропущенных случаев, а не редизайн: на всех разрешениях, где сейчас всё выглядит правильно, визуально ничего не должно измениться.

## Проверка

1. Для каждого блока, который правишь, — скриншот "было/стало" на ширинах: 320, 375, 768, 820, 1024, 1180, 1366, 1440, 1920, 2560px (там, где применимо по типу блока). На ширинах, которые уже были "опорными" для этого блока (границы текущих `@media`, обычные паспортные устройства) — визуальной разницы быть не должно вообще, сравнивай скриншоты пиксель в пиксель, не на глаз. На промежуточных и крайних ширинах — блок не должен обрезаться, наезжать на соседний контент или становиться непропорционально крупнее, чем был.
2. Список всех найденных и исправленных мест (файл/правило), с коротким обоснованием по каждому — почему это был реальный кандидат, а не намеренно фиксированное значение.
3. `npm run build` без ошибок, вес бандла не вырос.
4. Список того, что не удалось или в чём не уверен.
