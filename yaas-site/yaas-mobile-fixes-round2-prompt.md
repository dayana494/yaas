# YAAS — мобильные/планшетные правки: пины, dvh, свайп, контакты

Шесть отдельных проблем ниже 1024px. Часть из них — предположительно один и тот же
корневой баг (адресная строка мобильного браузера меняет `dvh` и ломает
`position: fixed`), часть — самостоятельные. По каждому пункту: подтвердить
диагноз на реальном телефоне/эмуляции, исправить, описать в отчёте, что было
не так на самом деле, если отличается от гипотезы ниже.

## 0. Общая гипотеза — читать первой

Несколько багов (п.1, п.2, п.3, отчасти п.6) физически совпадают: элемент
позиционируется или привязывается к `dvh`-величине, которая непрерывно
меняется, пока на мобильном скролле сворачивается/разворачивается адресная
строка. Два конкретных механизма:

- **GSAP `pin: true` без `pinType`.** По умолчанию GSAP пинит через
  `position: fixed`, который вычисляется относительно layout-вьюпорта. Когда
  адресная строка Safari/Chrome сворачивается на скролле, `fixed`-элемент
  визуально «прыгает» — это и есть «улетает наверх» / «не фиксируется на
  месте». Ни один пин в проекте не задаёт `pinType` явно:
  `grep -rn "pin: true" src` → `AdvantagesScreen.jsx:76`,
  `BrandTeaserScreen.jsx:354`, `FlavorStorySection.jsx:247`,
  `Footer.jsx:145`, `ScenarioArcGallery.jsx:354`, `ScenarioCards.jsx:61`,
  `ScenarioCardsIsometric.jsx:105`. Исправление — `pinType: 'transform'` для
  пинов, которые ниже 1024 остаются активными (сверить со списком: часть уже
  и так отключена ниже 1024 в отдельных компонентах, см. п.5).
- **`top`/`height` в `dvh` на элементах, которые не пересчитываются заново на
  каждый кадр.** Это прибито один раз при вёрстке и потом просто «плывёт»
  вместе с `dvh`, а не потому что кто-то двигает элемент. Пример —
  `styles/hero.css:254,296,305,311` (`top: 2.59dvh`, `top: calc(12dvh -
  5.35vw)`, `top: 29.8dvh`, `gap: 3.6dvh`) и `styles/contact.css:160`
  (`max-width: calc((100dvh - 2 * var(--block-gap)) * 370 / 760)`).

Не переписывать это глобальным свапом `dvh → svh` не глядя — на паре мест
`100vh; 100dvh` уже стоит нарочно парой (см. комментарий в
`styles/screen2.css:350`: «bare 100vh — вьюпорт со свёрнутой строкой, то есть
выше видимого»), это для высоты полноэкранных секций и трогать не надо.
Проблема — там, где `dvh` двигает контент (`top`, `max-width`), а не там, где
просто задаёт высоту блока.

## 1. Скрин 1 — карточки Screen 2 фиксируются слишком высоко

`components/ScenarioCardsIsometric.jsx:87-105`: `ScrollTrigger.create({
trigger: pinRef.current, pin: true, ... })`, без `pinType`. Карточка внутри
центрируется через `top/bottom: var(--iso-card-inset)` на
`.scenario-card-iso` (`styles/screen2.css:397-404`) — то есть центрирование
само по себе не привязано к `dvh`, значит именно сам пин (fixed +
схлопывание адресной строки) сдвигает всю секцию вверх от того места, где
она должна визуально стоять.

Исправление: `pinType: 'transform'` на этом триггере (и, вероятно, на
`ScenarioArcGallery.jsx:354`, который пинится прямо перед этой секцией и
измеряется как единая последовательность — см. `screen2-arc-target`). После
фикса проверить, что `ScenarioCardsIsometric.jsx:120-124`, где холостой
хвост пина синхронизирован с длиной, по-прежнему совпадает — `pinType:
transform` не меняет длину пина, только то, как элемент визуально держится,
но пересчитать `ScrollTrigger.refresh()` после смены пина на всякий случай.

**Причина для отчёта пользователю**: коротко объяснить, что GSAP пинит через
`position: fixed` по умолчанию, а фикс-позиционирование на мобильных
браузерах отсчитывается от layout-вьюпорта, который «дышит» вместе со
свёрткой адресной строки — отсюда видимый прыжок. `pinType: 'transform'`
вместо этого двигает элемент трансформом внутри обычного потока, который от
адресной строки не зависит.

## 2. Скрин 4/5 — текст под лого стоит выше, потом уезжает вниз

`styles/hero.css`, блок `@media (max-width: 1023px)`:
- `.hero-mobile-banner-logo-row { top: calc(12dvh - 5.35vw); ... }` (~296)
- `.hero-copy { top: 29.8dvh; ...; gap: 3.6dvh; }` (~296-311)
- `.hero-nav { top: 2.59dvh; }` (~254)

Все три — абсолютное позиционирование в `dvh` внутри `.hero-screen`
(`position: absolute; inset: 0`, ~28). Как только на скролле сворачивается
адресная строка, `dvh` растёт, и `top: 29.8dvh` в пикселях увеличивается —
блок с подзаголовком и кнопкой едет вниз. Это подтверждает гипотезу
пользователя: дело не в контенте, а в том, что вся геометрия героя завязана
на «дышащую» единицу.

Исправление — один из двух вариантов, выбрать по факту тестирования:
1. Заменить `dvh` на `svh` (small viewport height — фиксируется по
   развёрнутой адресной строке и не меняется на скролле) во всех
   `top`/`gap`-значениях этого мобильного блока (`2.59dvh`, `12dvh`, `29.8dvh`,
   `3.6dvh`). Плюс: ничего не ломает в разметке, минус: на очень короткой
   развёрнутой строке браузера герой будет чуть теснее, чем при свёрнутой —
   проверить, что подпись и кнопка не наезжают друг на друга при `svh`.
2. Зафиксировать высоту `.hero-screen`/`.hero-stage` один раз через JS
   (`window.visualViewport.height` или `window.innerHeight` в `resize`, не в
   `scroll`) в CSS-переменную и считать `top` от неё в `px`, а не в `dvh`
   напрямую — надёжнее, но требует нового слушателя вместо чистого CSS.

Начать с варианта 1 (`svh`), это тот же приём, что пользователь предлагает
для «всего сайта» в п.2 своего сообщения — заодно даёт «сайт помещается в
100% высоты экрана» без прыжков.

## 3. Скрин 2 — банка с карточки вкуса улетает; свайп → только стрелки; клик по банке

Три отдельных изменения в одном месте (`pages/HomePage.jsx`,
`three/CanRig.jsx`).

**3a. Банка не фиксируется.** Тот же корневой баг, что в п.1: вход в
интерактивное окно интро управляется через `ScrollTrigger.create({ ...
pin: true ... })` в `pages/HomePage.jsx:509` (entranceTrigger) и `:581`
(detail-триггер, `end: () => \`+=${introUnitsPx(INTERACTIVE_UNITS)}\``) —
без `pinType`. Добавить `pinType: 'transform'` туда же.

**3b. Свайп меняет вкус вместо стрелок.** Сейчас переключение вкуса ниже
1024 идёт через тот же скролл-scrub, что ведёт 3D-сцену (`INTERACTIVE_UNITS`
окно в `HomePage.jsx:581-614`, значение прогресса передаётся в `CanRig`
через `api.setDetailProgress`). Отдельного свайп-жеста нет —
`dragBy(deltaSlots)` в `three/CanRig.jsx:477-487` объявлен, но нигде не
вызывается (`grep -rn "dragBy" src` — только объявление). То есть то, что
выглядит как «смена по свайпу», на самом деле смена по вертикальному
скроллу страницы поверх пина: любое касание и движение пальцем в этой
секции интерпретируется как скролл и двигает `INTERACTIVE_UNITS`-прогресс, а
значит и активный вкус.

Нужно: ниже 1024 отвязать выбор активного вкуса (`setActiveFlavor`,
`handlePickFlavor` в `HomePage.jsx:344-351`) от скролл-scrub и оставить
только стрелки. Практически — завести флаг (`matchMedia('(max-width:
1023px)')`, как в `Footer.jsx:134`) и на мобильном не подключать
scroll-триггер, который меняет `activeFlavor` по прогрессу (тот, что качает
прогресс в `CanRig` между `ENTRANCE_UNITS` и концом `INTERACTIVE_UNITS` —
искать в `HomePage.jsx` вокруг `:535-614`, где написано «interactive
window»). Сам скролл продолжает управлять входом/выходом из интро (это не
трогаем), просто не должен больше листать вкусы — вкусы листаются только
`handlePickFlavor` от стрелок, которые уже есть и уже работают
(`onClick`-обвязка стрелок — найти в JSX рендере `HomePage.jsx`, где
рендерится `FlavorGallery`/стрелки, и подтвердить, что `handlePickFlavor`
уже на них навешан).

**3c. Клик по банке открывает карточку вкуса.** `handleEnter` в
`HomePage.jsx:358-368` уже существует и работает по тапу на центральную
банку (`gsap.to(window, { scrollTo: { y: trigger.end } })`), значит клик
частично уже работает — проверить, что на мобильном обработчик клика
действительно навешан на 3D-канвас/меш активной банки (Three.js
raycaster/`onClick` в `CanRig.jsx` или в обёртке `<Canvas>` в
`pages/HomePage.jsx`), а не только на десктопе. Если обработчика на мобиле
нет — добавить его на touch/click события того же меша, что и на десктопе,
не создавая второй код-путь.

## 4. Скрин 3 — заголовок сначала уже, потом расширяется до нужной ширины

Заголовок — `.screen2-h2` (`styles/screen2.css:165-181`), рендерится через
`SectionHeading` → `DropText` (`data/featureFlags.js: HEADING_ANIMATION =
'drop'`), вызывается из `components/ScenarioArcGallery.jsx:400-407`. У
`.screen2-h2` нет мобильного переопределения — `max-width: clamp(320px,
62vw, 1160px)` действует и на телефоне тоже, но это не должно давать
«сначала уже, потом шире»: `62vw` от ширины экрана не меняется на скролле
(в отличие от `dvh`, `vw` не плавает от адресной строки).

Два кандидата на причину, проверить оба на реальном устройстве:
1. **FOUT/reflow шрифта.** В `DropText.jsx` слова/символы оборачиваются в
   `[data-drop-piece]`-спаны и анимируются через `transform`/`opacity`
   (`DropText.jsx:113-130`) — трансформ не должен менять раскладку. Но если
   `--font-display` (Soledago/Bounded, см. git-лог «Serve Soledago and
   Bounded as WOFF2 with OTF/TTF fallback») ещё не загружен в момент, когда
   `IntersectionObserver` в `DropText.jsx:155-178` запускает анимацию,
   заголовок рисуется сначала фолбэк-шрифтом (обычно уже) и переверстывается
   на широкий `--font-display` после `document.fonts.ready`. Проверить:
   `document.fonts.ready` до или после первого пейнта секции на медленном
   3G/4×CPU throttling — если разрыв большой, обернуть рендер текста (или
   хотя бы его измерение под `text-wrap: balance`) в ожидание
   `document.fonts.ready`, либо предзагрузить шрифт заранее (`<link
   rel="preload">` уже есть/нет — проверить `index.html`).
2. **`text-wrap: balance` пересчитывается уже после первого рендера с
   другой шириной контейнера** — если родитель `.screen2-headline`
   (`width: 100%; padding: 0 30px`, `screen2.css:160-163`) в момент первого
   рендера ещё не получил свою финальную ширину (например, пин ещё не
   применился/спейсер ещё не вставлен), браузер посчитает `balance` по
   временной узкой ширине и не пересчитает, пока не будет явного relayout.
   Проверить, не помогает ли принудительный `getBoundingClientRect()`-тук
   или смена `text-wrap` на `pretty`/`normal` для мобильного заголовка.

Пофиксить причину, которая подтвердится, и коротко описать её в отчёте —
это тот случай, где догадка может не совпасть с реальностью.

## 5. Фоны в блоках преимуществ и «о бренде» должны быть фиксированными

Сейчас это осознанно отключено ниже 1024, см. комментарии:
`styles/advantages.css:485-495` и `styles/brand-teaser.css:298-313` — оба
блока explicitly говорят «backdrop driver не подключается ниже 1024,
поэтому ничего не переключает фон в fixed» и переводят
`.advantages-bg`/`.about-brand-bg` в `position: absolute; inset: 0; height:
auto`, то есть фон растягивается на всю высоту родителя и скроллится вместе
с ним. Драйверы, которые на десктопе переключают класс `is-fixed`/`is-parked`
— `createViewportBackdropDriver('.about-brand', '.about-brand-bg')` и
`createFallDriver(['.advantages', '.about-brand'])`, обе строки
`HomePage.jsx:480/488` — не запускаются ниже 1024 намеренно (видимо, из-за
того же fixed+dvh прыжка, что и в п.1/2/3).

Раз `pinType: 'transform'` (п.1) должен снять причину, по которой
`position: fixed` дёргается на мобильном — включить фиксированный фон ниже
1024 заново:
1. Убрать ограничение `@media (max-width: 1023px)` для `.advantages-bg` и
   `.about-brand-bg`, вернув им `is-fixed`/`is-parked` поведение как на
   десктопе (или сделать более лёгкую мобильную версию — `position: sticky;
   top: 0` на фоне внутри секции, если секция выше вьюпорта, что не требует
   JS-driver вообще и не зависит от адресной строки — оценить оба варианта
   и выбрать тот, что не даёт видимых скачков на реальном телефоне).
2. Если решите оставить драйверный подход — подключить
   `createViewportBackdropDriver`/`createFallDriver` и ниже 1024 (убрать
   мобильное исключение в `HomePage.jsx`, если оно там есть — проверить, не
   ограничены ли вызовы `matchMedia` где-то выше по файлу).
3. В любом случае заменить `100dvh` в `.advantages-bg`/`.about-brand-bg`
   (`advantages.css:340`, `brand-teaser.css:104-105`) на `100svh`, чтобы
   высота фонового слоя не плавала при сворачивании адресной строки — то же
   рассуждение, что в п.2.

## 6. Плашка контактов — не на всю ширину, гуляет при скролле, нужна высота на весь экран

`styles/contact.css:141-207`, мобильный блок:

```
.contact-panel {
  aspect-ratio: 370 / 760;
  max-width: calc((100dvh - 2 * var(--block-gap)) * 370 / 760);
  ...
}
```

Здесь сразу два бага:
1. **Не во всю ширину.** Ширина панели считается не от контейнера, а от
   доступной высоты (`100dvh - 2*120px` на большинстве телефонов даёт
   ширину заметно меньше 100% контейнера — отсюда «плашка уже, чем везде на
   сайте»). Это осознанный компромисс автора (см. комментарий над правилом:
   «панель должна помещаться по высоте, иначе обрезается»), но пользователь
   хочет обратное — ширина как у остального контента, высота подстраивается
   под то, что осталось.
2. **Гуляет при скролле.** `100dvh` в этой формуле пересчитывается, пока
   меняется адресная строка → `max-width` панели меняется на лету → видно,
   как панель «расширяется».

Исправление по ТЗ пользователя:
- Ширина: убрать `max-width`, посчитанный от высоты; панель должна занимать
  ту же ширину, что и остальные секции на этой ширине экрана — то есть
  просто `width: 100%` внутри `.contact-frame` (тот же `padding: 0 2.56vw`,
  что уже стоит, `contact.css:145`), без привязки к `aspect-ratio` по
  ширине.
- Высота: «на всю высоту экрана с отступами 20px сверху и снизу» — то есть
  `height: calc(100svh - 40px)` (не `dvh` — см. рассуждение в п.0/2, чтобы
  высота не прыгала при скролле), а не `aspect-ratio` вовсе. Убрать
  `aspect-ratio: 370/760` и `min-height: 420px` на этой ширине, если высота
  теперь задаётся явно; внутренняя раскладка (`padding-top: 21.6%` и
  остальные проценты в `contact.css:165-207`) считалась от ширины панели
  (370 из 390) — пересчитать проценты, которые должны быть привязаны к
  высоте, под новую геометрию, и проверить на реальных пропорциях экрана
  (390×844, 375×667, 412×915), что контент (заголовок, кнопки, банки) не
  вылезает и не сжимается неестественно.
- Учесть `--block-gap` — на этой ширине он равен `80px`
  (`styles/index.css:60-62`), не `120px`; пользователь просит именно `20px`
  сверху/снизу для самой плашки, а не переиспользовать `--block-gap` —
  завести отдельную величину (например `--contact-panel-inset: 20px`) вместо
  подмены `--block-gap`, чтобы не задеть отступ `.contact { padding:
  var(--block-gap) 0; }` вокруг всей секции (`contact.css:15`), который,
  похоже, менять не просили.

## Что не трогать

- Desktop (≥1024) — без изменений. Все правки — внутри `@media (max-width:
  1023px)` или за `matchMedia`/аналогичным условием в JS.
- Общая логика rise/fall-переходов между блоками (описана и уже исправлена в
  отдельном промпте `yaas-mobile-no-overlap-scroll-prompt.md`, если та
  задача уже выполнена — не откатывать её правки).
- Содержимое анимаций (DropText-эффект как таковой, 3D-сцена банок,
  isometric-переворот карточек) — трогаем только геометрию/позиционирование,
  не сам художественный эффект.

## Проверка

1. Реальные устройства или DevTools-эмуляция с включённым «show device
   frame» (эмуляция схлопывающейся адресной строки не всегда точна в
   DevTools — по возможности проверить на живом iPhone Safari и Android
   Chrome, где эффект адресной строки настоящий).
2. По каждому пункту — видео/скринкаст быстрого скролла вниз и вверх через
   весь сайт на 390×844 и 768×1024.
3. `grep -n "pin: true" src -r` — свериться, что везде, где пин остаётся
   активным ниже 1024, стоит `pinType: 'transform'`.
4. `grep -n "dvh" src/styles -r` — по каждому оставшемуся `dvh` короткая
   заметка в отчёте: это высота блока (ок, не трогали) или позиция/размер,
   который плавает (должен был стать `svh` или пофикситься иначе).
5. Свайп по 3D-галерее вкусов на телефоне не меняет активный вкус; стрелки
   меняют; тап по центральной банке открывает карточку вкуса.
6. Контактная плашка: ширина совпадает с шириной остального контента на
   той же ширине экрана; высота = `100svh - 40px`; не меняется во время
   скролла ни по ширине, ни по высоте.

## Отчёт

По каждому из 6 пунктов: что оказалось настоящей причиной (совпало с
гипотезой выше или нет), что изменено, какие файлы. Отдельно — список
`dvh`-мест, которые оставлены как есть, с однострочным обоснованием.
