# YAAS — реальное устройство трясётся на скролле; карточки сценариев всё ещё не держатся

## Найденная причина

`pages/HomePage.jsx:169-332`, эффект `correctPinStarts` (добавлен в
88f7566 «Fix the mobile pins, address-bar drift…»). Он навешан на
`window.addEventListener('resize', onResize)` (строка ~325-332), с
дебаунсом 250мс, и при срабатывании убивает и заново создаёт 5
ScrollTrigger'ов подряд: arc-галерею, карточки сценариев
(`SCENARIO_CARDS_TRIGGER_ID`), advantages, about-the-brand, футер —
каждый через `trigger.kill(true, true)` + новый `ScrollTrigger.create()`,
плюс общий `ScrollTrigger.refresh()` в конце.

На мобильных браузерах (Safari iOS, Chrome Android) `window.innerHeight`
меняется и стреляет событием `resize` каждый раз, когда во время скролла
сворачивается или разворачивается адресная строка — это происходит
многократно за один жест скролла, а не только при повороте экрана или
реальном ресайзе окна. Код это не различает: любой `resize`, включая
шумовой от адресной строки, перезапускает `correctPinStarts` — то есть
прямо посреди скролла несколько раз убиваются и пересоздаются все пины
страницы. Это и есть тряска на реальном устройстве.

Для карточек сценариев это к тому же ломает сам расчёт: `slotTop()`
(строка ~192) предполагает, что измерение идёт до начала скролла
(`scrollY` близко к 0, ничего ещё не запинено — см. собственный
комментарий в коде: «this pass runs… scrollY is still 0 here, before the
user has scrolled at all»). Когда `onResize` вызывает его повторно
посреди активного скролла, это предположение уже неверно: часть секций
может быть в запиненном состоянии, `scrollY` не 0 — новая посчитанная
`start`-позиция для карточек может оказаться ошибочной, и пин остаётся
сломанным даже после фикса `pinType`.

То же самое, без фильтрации, стоит ещё в нескольких местах — они дешевле
(не пересоздают ScrollTrigger'ы), но тоже лишний раз срабатывают на
каждое «дыхание» адресной строки и вносят свою часть тряски:
- `scroll/riseTransition.js:120` (`driveRise` на resize)
- `components/Footer.jsx:83`
- `components/HeroWordmark.jsx:75,142`
- `components/FlavorStorySection.jsx:198`
- `components/FlavorGallery.jsx:34`
- `hooks/useHeroScale.js:44`
- `gradient/createGradient.js:298`
- `pages/HomePage.jsx:467-472` (`onIntroResize`, отдельный от
  `correctPinStarts`, тоже трогает высоту `.intro-wrap`)

## Фикс

Завести один общий хелпер вместо `window.addEventListener('resize', fn)`
россыпью по всем этим файлам — он должен звать `fn` только на настоящий
resize (смена ширины, поворот экрана), а не на изменение одной высоты от
адресной строки:

```js
// например, в scroll/riseTransition.js или отдельном src/utils/onRealResize.js
export function onRealResize(handler) {
  let lastWidth = window.innerWidth;
  const onResize = () => {
    const width = window.innerWidth;
    if (width === lastWidth) return; // высота одна поменялась — адресная строка, игнорируем
    lastWidth = width;
    handler();
  };
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}
```

Заменить им `window.addEventListener('resize', ...)` во всех перечисленных
местах, включая `HomePage.jsx`'s `onResize` (correctPinStarts) и
`onIntroResize`. Ширина — надёжный сигнал: адресная строка мобильного
браузера меняет только `innerHeight`, ширина вьюпорта остаётся той же, а
настоящий ресайз (десктопное окно, поворот телефона) почти всегда меняет
и ширину тоже.

Отдельно для `correctPinStarts` — дополнительно проверить, что даже при
настоящем resize пересоздание пинов не запускается посреди активного
жеста скролла: например, отложить вызов до следующего `scrollend`
(или, если браузер не поддерживает — таймер тишины: ничего не делать,
если `Date.now() - lastScrollTime < 300` на момент срабатывания), чтобы
поворот экрана посреди инерционного скролла тоже не дёргал секции.

## Проверка

1. Реальное устройство (не эмуляция DevTools — там сворачивание адресной
   строки не воспроизводится честно): медленный и быстрый скролл вниз и
   вверх по всей главной странице, iOS Safari и Android Chrome. Тряски или
   рывков быть не должно.
2. Убедиться, что `console.log` (временный, для проверки, убрать перед
   коммитом) в `correctPinStarts` не вызывается повторно во время
   активного скролла — только при реальном повороте/ресайзе.
3. Карточки сценариев (`.scenario-cards-iso`): при пине карточки должны
   стоять по центру и не «улетать», один и тот же результат при первом
   заходе на страницу и после нескольких циклов скролл-вверх/вниз подряд.
4. Повернуть телефон альбомно/портретно во время нахождения на любом
   пинящемся блоке — позиции пинов должны пересчитаться один раз и
   корректно, без тряски.
